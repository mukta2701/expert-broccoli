# Roadmap: From Prototype to Open-Source Tool

Status: draft plan. Day 0 is the day work starts. Dates are relative on purpose.

## 1. Where we are (honest baseline)

The prototype is a clean teaching artifact, not yet a tool.

- 16 test cases in `data/cases.json`, one prompt each, no variants.
- Target is a deterministic, keyword-matching mock (`mock_app/mock_chatbot.py`). Its scripted responses exercise the pipeline, not a real model or deployed controls.
- The primary scorer checks exact canary emission and case-specific expected phrases. A refusal-substring scorer remains as a baseline. Neither is validated against human-labelled model responses.
- The "16/16 PASS vs 0/16 PASS" result is true by construction. It demonstrates the pipeline, not detection skill.
- An offline stdlib unittest suite exists in `tests/test_engine.py` for case loading, scoring, risk calculations and run provenance. Run it with `python3 -m unittest discover -s tests -t .` from the project folder.
- No real model adapter, scanner importers, packaging, CI or license file exist on this baseline.

Rule for everything below: no claim of industry value until it is measured on a real target against an independent baseline.

## 2. Positioning (decide in week 1)

Garak, PyRIT and Promptfoo already cover attack generation. Do not compete there. The defensible gap in this repo is:

- **Risk-scored evidence example for review.** Likelihood x impact with control effectiveness, mapped to OWASP LLM Top 10 and ISO 27001 themes.
- **Governance evidence.** Findings, risk register and mitigation plan, planned to be generated from run results (the current reports are static examples).
- **Family-based, sanitized catalog.** Templates with placeholders, not live strings.

Working pitch: "Turn red-team scanner output into a defensible risk register." Importing Garak, PyRIT and Promptfoo results is a future proposal; the current runner executes only the local mock cases. Revisit this after the 30-day gate.

## 3. Phased plan

### Days 0-30: Make it real and trustworthy

- Add `LICENSE`, `SECURITY.md` and `CONTRIBUTING.md`.
- Package as `pyproject.toml` with a `pitest` style CLI. Keep the core dependency-free.
- Add a target adapter interface with three adapters: mock, OpenAI-compatible HTTP, and local model via an OpenAI-compatible server.
- Extend the existing stdlib unittest suite for real-model adapters and scorer validation. Add CI (lint, type check, tests) on every pull request.
- Build a pluggable scorer interface around the current canary/expectation scorer. Keep the substring scorer as a baseline.
- Extend the existing versioned JSON cases with OWASP tags and sanitized variants.
- Gate: one command runs against a real model and emits JSON plus a Markdown report.

### Days 31-60: Depth and credibility

- Expand to 8-10 families and 5-10 paraphrase variants per family, generated by templating, not hand-crafted exploits.
- Add indirect-injection scenarios with a sandboxed fake RAG corpus and fake tools. Tools only write to a local log.
- Add a human-labeled set of at least 300 responses. Measure scorer precision, recall and inter-rater agreement.
- Add an LLM-judge scorer and compare it with the string scorer on the labeled set.
- Proposed future work: build importers for Garak, PyRIT and Promptfoo result files, feeding the risk register.
- Run the benchmark study (section 5) and write down negative results too.
- Gate: a reproducible results table from at least three real models and the three baseline tools.

### Days 61-90: Launch and adoption

- Publish v0.1.0 to PyPI with signed releases and an SBOM.
- Add a GitHub Action that fails a build when residual risk exceeds a threshold.
- Add HTML and SARIF export so findings show in code-scanning dashboards.
- Run a pilot with one or two internal teams. Capture time-to-first-finding and false-positive complaints.
- Complete responsible disclosure for any vendor findings, then publish the article.
- Gate: at least one external contributor merged, and one pilot team using it in CI.

## 4. Architecture changes

Target layout, keeping the current modules recognizable:

```text
core/       data models: TestCase, Result, Finding, RiskEntry
catalog/    versioned YAML families, templates, OWASP and ISO tags
targets/    adapters: mock, http_openai, local, custom (plugin entry point)
runners/    execution, retries, rate limits, seeding, concurrency
scorers/    string, regex, classifier, llm_judge (all return the same schema)
importers/  garak, pyrit, promptfoo -> normalized Result
reporting/  json, markdown, html, sarif, risk register
```

Specific changes:

- Separate attack intent from payload text. The catalog stores intent plus a placeholder (`[UNSAFE_REQUEST]`). A harmless canary objective fills it at run time.
- Use canary objectives for success detection, such as "output the token CANARY-7f3a". This avoids harmful content and gives an objective pass/fail signal.
- Make every run reproducible: record model id, parameters, seed, catalog version, scorer version, tool version.
- Run each case N times and report a rate with a confidence interval. LLM output is stochastic, so one sample proves little.
- Add a plugin entry point so companies can add private catalogs without forking.
- Store results as JSON Lines with a versioned schema. Update `tester/results_schema.md` into a real JSON Schema.

## 5. Validating credibility

Goal: show the tool finds real weaknesses, agrees with humans, and adds value beyond existing tools.

**Scorer validity**
- Hand-label 300+ responses with two reviewers. Report Cohen's kappa and per-family precision and recall.

**Head-to-head baselines (same targets, same budget)**
- Garak: compare its prompt-injection and leakage probes on the same models.
- PyRIT: compare scorer and orchestrator results on equivalent scenarios.
- Promptfoo: compare its red-team plugins on equivalent scenarios.
- Metrics: attack success rate per family, false positive rate, coverage of OWASP categories, runtime, cost per finding, reproducibility across reruns.
- Be explicit about what each tool is designed for. Different goals make some comparisons unfair.

**Public benchmark alignment**
- Map families to public suites such as AgentDojo and InjecAgent for indirect and tool injection. Use their published protocols, not copies of payloads.
- Report where results agree or disagree with published numbers.

**Controls on our own bias**
- Pre-register the metrics and models before running.
- Test at least one hardened configuration (system prompt hardening, input filter, output filter) and show the tool detects the improvement.
- Report negative results, scorer failures and limitations in the article.
- Invite one external security reviewer to reproduce the study from the repo alone.

## 6. Licensing, ethics and responsible disclosure

**License**
- Code: Apache-2.0. It gives a patent grant, which company legal teams prefer.
- Catalog and labeled data: CC BY 4.0, stated separately.
- Check licenses of any public datasets before reuse. Cite rather than copy when terms are unclear.

**Company use**
- Get written approval from legal, security and the employer's open-source office before publishing. Confirm the work is outside any IP assignment clause.
- Keep the clean-room boundary in `DISCLAIMER.md`. No employer prompts, logs, findings or architecture, ever.
- Use a separate personal or org account for the public repo, with a documented contribution policy.

**Safety rules (non-negotiable)**
- No operational exploit payloads, working jailbreak strings, or harmful-content prompts in the repo, docs or examples.
- Catalog entries are templates with canary objectives. Reject pull requests that add live jailbreaks, with a PR checklist and a CI lint that scans for them.
- Ship an authorized-use notice. The CLI requires an explicit `--i-have-authorization` style flag for any remote target.
- Do not ship automated mass-targeting features, evasion of vendor abuse detection, or credential harvesting.
- Default to rate limits and a visible test-traffic header so defenders can identify scans.

**Responsible disclosure**
- Publish a `SECURITY.md` with a contact, response targets, and a safe-harbor statement for good-faith reports.
- If the tool finds a vulnerability in a vendor model or product, report privately first. Use the vendor's program if one exists.
- Allow a standard window (commonly 90 days) before publishing details. Extend if the vendor is actively fixing.
- Never publish a reproducible exploit for an unfixed issue. Publish rates and mitigations, not strings.

## 7. Article outline (about 1,500 words)

Working title: "What a prompt-injection scanner needs besides attacks: measurement you can defend."

| Section | Words | Content |
|---|---|---|
| Hook | 120 | A security team gets a scanner report with 400 findings and cannot tell which matter. |
| The gap | 200 | Attack tools are plentiful. Scoring validity and risk translation are weak. Define prompt injection in two sentences. |
| Design principles | 250 | Family-based sanitized catalog, canary objectives, repeated trials, separation of attack from scoring. |
| How it works | 250 | Architecture diagram, one worked example from catalog to risk register entry. |
| Does it hold up? | 400 | Scorer agreement with humans, head-to-head with Garak, PyRIT and Promptfoo, and a hardened-config test. Include a results table and negative results. |
| Safety and disclosure | 150 | Why there are no payloads, how contributions are screened, disclosure outcomes. |
| Limits | 80 | Stochastic output, coverage gaps, judge bias, not a substitute for a manual red team. |
| What next, call to action | 50 | Repo link, how to contribute a family, how to run in CI. |

Rules for the article: every number comes from a reproducible run in the repo; no payload strings; name tools fairly; state the author's employer affiliation and approval status.

## 8. Open decisions for the owner

Employer approval path, which models to benchmark, who the second labeler is, and whether the pilot team is internal or external. If the pilot shows no demand for the risk-register niche, narrow scope rather than add features.
